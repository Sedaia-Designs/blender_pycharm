# IntelliJ Marketplace API Warning Remediation Plan

Scope: resolve or explicitly classify the API warnings reported by IntelliJ Marketplace for Blender Development 1.0.0-beta.2 on PyCharm 2026.1 and 2026.2.1. The work covers the scheduled-for-removal list renderer, inherited `ToolWindowFactory` warnings, project-wizard error reporting, and debugger-session startup. Feature changes and changing the minimum supported PyCharm version are initially out of scope.

## Marketplace evidence

- PyCharm 2026.2.1 RC (`PY-262.9437.71`) reports:
  - one scheduled-for-removal call to `SimpleListCellRenderer.create(String, Function)`;
  - four deprecated `ToolWindowFactory` method usages;
  - eight experimental API usages involving `ToolWindowFactory` and `MessageError`.
- PyCharm 2026.1 (`PY-261.27258.30`) reports:
  - four deprecated `ToolWindowFactory` method usages;
  - eleven experimental API usages involving `ToolWindowFactory`, `MessageError`, and `XDebugSessionBuilder`.
- Both Marketplace targets are reported as compatible. These findings are API-lifecycle warnings rather than current binary incompatibilities.
- The debugger-builder warning is version-dependent: it appears on 261 but not 262. The list-renderer removal warning appears on 262.
- The plugin currently declares `sinceBuild = "261"`; remediation must preserve 261 compatibility unless a separate support-policy change is approved.

## Work plan

- [x] Capture a reproducible Plugin Verifier baseline for `PY-261.27258.30` and `PY-262.9437.71`.
  - Save the complete reports and map every bytecode finding to a source declaration or compiler-generated bridge.
  - Confirm why the verifier counts each inherited `ToolWindowFactory` method twice when the project contains one source implementation.
  - Record warning counts by IDE target so version-specific changes remain visible.
- [x] Replace the scheduled-for-removal list renderer in `BlenderExtensionBuildSettingsEditor`.
  - Replace `SimpleListCellRenderer.create(...)` with the supported UI DSL `textListCellRenderer(...)` API.
  - Preserve the existing null/empty presentation and `BlenderExtensionBuildOperation.presentableName()` mapping.
  - Add or update a focused settings-editor test if the renderer can be exercised without disproportionate platform-fixture setup.
- [x] Investigate the deprecated and experimental `ToolWindowFactory` findings.
  - Verify whether `isApplicable(Project)`, `isDoNotActivateOnStart`, `anchor`, `icon`, and `manage(...)` are reported solely because Kotlin emits compatibility bridges for interface defaults.
  - Keep icon, anchor, and startup-activation behavior declarative in `plugin.xml` where the extension schema supports it.
  - Override `isApplicableAsync(Project)` only if the tool window needs real applicability logic; do not add meaningless overrides solely to move verifier warnings.
  - If the warnings are unavoidable artifacts of implementing the platform interface, document them as upstream/interface-generated findings with supporting verifier and bytecode evidence.
- [ ] Remove direct plugin construction of experimental `MessageError` where a stable boundary exists.
  - Evaluate the higher-level `Result.localizedError(...)` factory and inspect its generated bytecode on both supported IDE lines.
  - Use the replacement only if it removes the plugin's direct experimental reference without introducing an equally unstable dependency.
  - Preserve localized user feedback, diagnostic logging, and `CancellationException` propagation.
  - Add a project-generation failure test that verifies a localized, user-readable failure result.

  - Check whether a stable 261-compatible API can preserve execution-environment association, process-handler ownership, content reuse, and debugger-session startup.
  - Prefer retaining a narrowly isolated 261-only experimental reference over replacing it with a deprecated API that creates a different compatibility risk.
  - Escalate dropping 261 support as a separate product decision only if no supported implementation can satisfy the debugger lifecycle contract.
- [ ] Add or update regression coverage proportional to each accepted code change.
  - Verify extension-build operation rendering.
  - Verify project-generation failures remain localized and cancellation is not converted into failure.
  - Verify debugger attach success, startup failure, termination propagation, and path mapping on both supported IDE lines.
  - Verify the Blender tool window still registers, initializes lazily, and disposes its content correctly.

  - Run `./gradlew compileKotlin --no-daemon`.
  - Run `verifyPlugin` and Plugin Verifier against `PY-261.27258.30` and `PY-262.9437.71`.
  - Compare the final reports with the saved baseline and classify every remaining warning as resolved, version-limited, or compiler/platform-generated.
  - Manually exercise the extension-build selector, tool-window opening, project-generation error path, and Blender debugger attach lifecycle in IDE sandboxes.

  - Add a concise changelog entry for user-relevant compatibility improvements.
  - Update Blender Developer Docs only if supported IDE versions, setup steps, or debugger behavior change.
  - Keep implementation-only warning cleanup out of public documentation when it does not affect users.
- [ ] Commit Changes.

  - Use the repository's `[Type -> module] Description` commit format.

## Phase 1 baseline results

- The Gradle verifier matrix resolves the exact requested PyCharm Professional builds:
  - `PY-261.27258.30`;
  - `PY-262.9437.71`.
- IntelliJ Plugin Verifier 1.409 writes the complete HTML reports to:
  - `build/reports/pluginVerifier/PY-261.27258.30/report.html`;
  - `build/reports/pluginVerifier/PY-262.9437.71/report.html`.
- The local 261 report contains four deprecated `ToolWindowFactory` findings and nine experimental findings:
  - six generated `ToolWindowFactory` findings;
  - three explicit `XDebugSessionBuilder` references in `BlenderDebugAttachService.attachWithPydevClientMode(...)`.
- The local 262 report contains one scheduled-for-removal renderer finding, four deprecated `ToolWindowFactory` findings, and six experimental `ToolWindowFactory` findings.
- `javap` confirms that Kotlin emitted delegating methods for all default members of `ToolWindowFactory`, including `isApplicable`, `isDoNotActivateOnStart`, `anchor`, `icon`, and `manage`. The verifier counts each affected member once as an override and once as an invocation of the interface default.
- `SimpleListCellRenderer.create(...)`, `XDebugSessionBuilder.environment(...)`, and `XDebugSessionBuilder.startSession()` are explicit plugin bytecode calls and therefore have direct source remediation points.
- `BlenderProjectGenerator.generateNewProject(...)` directly constructs `MessageError` in packaged bytecode, matching the Marketplace warning even though it is absent from the local verifier totals.
- Both local verifications currently report an unresolved mandatory dependency on `com.intellij.modules.python`. This causes the verifier to omit the two `MessageError` experimental findings and report 9/6 experimental usages instead of Marketplace's 11/8. Correcting that dependency input remains a validation prerequisite; the resulting unresolved `com.jetbrains.python` compatibility finding is not treated as evidence of an API removal.
- The verifier task exits unsuccessfully because of that unresolved dependency-derived compatibility finding. Report generation itself completes for both targets.

## Phase 3 tool-window findings

- Kotlin's default `JvmDefaultMode.ENABLE` emits compatibility methods in implementing classes when a Kotlin interface supplies JVM defaults. In `BlenderToolWindowFactory`, those generated methods delegated to `ToolWindowFactory.isApplicable`, `isDoNotActivateOnStart`, `anchor`, `icon`, and `manage`.
- Plugin Verifier counted each deprecated or experimental generated method twice: once as an override and once as the invocation of the interface default.
- The project now compiles with `JvmDefaultMode.NO_COMPATIBILITY`. The packaged `BlenderToolWindowFactory` bytecode contains only the constructor, `createToolWindowContent`, and its implementation lambdas; it inherits all other behavior directly from the platform interface.
- The module-wide compiler setting is acceptable for this plugin because every project-owned Kotlin interface is `internal`; the plugin does not publish a Kotlin interface ABI for external consumers that depend on legacy `DefaultImpls` accessors.
- Tool-window icon and anchor remain declarative in `plugin.xml`. The factory has no applicability condition, custom icon/anchor implementation, or management lifecycle behavior that would justify source overrides.
- Plugin Verifier reports no deprecated or experimental `ToolWindowFactory` usage on either `PY-261.27258.30` or `PY-262.9437.71`. The 262 report now contains no API-lifecycle warnings, while the 261 report contains only the three explicit `XDebugSessionBuilder` findings.
- Focused tool-window tests pass. The full suite completes 181 of 183 tests; the two existing `BlenderProjectGeneratorTest` failures still originate in `VueLspServerLoader` initialization and stale index state.

## Recommended decision order

1. Replace the renderer because IntelliJ provides a direct supported successor.
2. Test the localized-result factory because it may remove the direct `MessageError` reference without changing behavior.
3. Establish whether the `ToolWindowFactory` findings are generated artifacts before changing source code.
4. Retain the modern debugger builder unless evidence identifies a stable 261-compatible alternative or a support-policy change is approved.

## Risks and decision points

- Replacing a warning-producing API with a deprecated predecessor lowers no meaningful compatibility risk. Warning count is a diagnostic signal, not the sole success criterion.
- Kotlin interface compatibility bridges can create verifier findings that have no explicit source call site. Source overrides should be added only when they express real plugin behavior.
- A wrapper around an experimental type does not necessarily remove the dependency: method signatures and inlined factories can still leave references in compiled bytecode. Verification must inspect the packaged plugin rather than source imports alone.
- Debugger startup owns more than session creation. Any alternative must preserve the `ExecutionEnvironment`, `ProcessHandler`, run-content lifecycle, and termination callbacks.
- Dropping the 261 target could remove the debugger warning, but it would narrow the plugin's declared compatibility and therefore requires an explicit product decision.
