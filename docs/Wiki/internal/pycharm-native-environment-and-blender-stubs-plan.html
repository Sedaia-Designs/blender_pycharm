PyCharm Native Environment and Blender Stubs Plan

Implementation plan for the Blender new-project wizard on PyCharm 2026.1+

Scope: reuse PyCharm environment creation and SDK assignment, retain ownership of Blender-specific project generation, and install version-matched fake-bpy-module linting stubs. Unrelated run/debug and existing-project workflows are out of scope.

1) Source-Grounded Facts

  • PyV3ProjectBaseGenerator is a DirectoryProjectGenerator intended to connect Python project-specific settings and UI to PyCharm's new-project workflow.
  • Its base generation flow creates or selects a Python SDK, assigns it to the supplied module, and then calls PyV3ProjectTypeSpecificSettings.generateProject(module, baseDir, sdk).
  • PyV3ProjectTypeSpecificUI provides an upper settings area and an Advanced Settings area around PyCharm's environment controls.
  • PythonPackageManager.forSdk(project, sdk) selects a package-manager implementation for the configured SDK. The API is experimental and parts of package installation are internal.
  • The upstream fake-bpy-module documentation defines version-specific packages named fake-bpy-module-<Blender major.minor> and lists packages for Blender 4.2, 4.5, and 5.1.
  • Standalone PyCharm testing confirms that IntelliSense resolves the stubs when the package is installed into the selected SDK's site-packages. For unpacked or pre-generated modules outside the SDK, the directory containing the top-level stub modules must instead be attached to the project as a Sources Root.
  • The current BlenderVersions table contains Blender 4.2, 4.5, and 5.2. The supplied upstream documentation does not yet confirm a fake-bpy-module-5.2 package.
  • PluginConfig.bpyApiInstallPath already provides an application-level directory for storing fake-bpy code-completion files.
  • Before the foundation phase, the plugin wrapped a generic GeneratorNewProjectWizard in a legacy directory-generator adapter and asked users to configure an interpreter and install fake-bpy-module manually.

2) Architecture Decisions

DecisionRationale
Extend PyV3ProjectBaseGenerator Reuse PyCharm's supported environment UI, SDK creation, module assignment, progress, and error lifecycle.
Do not copy PyCharm environment sources A source copy would depend on numerous internal UI, interpreter, Eel, conda, uv, and navigation types that may change between IDE builds.
Set supportsNotEmptyModuleStructure to false The Blender generator remains the only owner of src, templates, and pyproject.toml.
Own Blender settings and UI Blender metadata, manifest validation, permissions, templates, and project defaults remain independent of PyCharm implementation details.
Hide packaging APIs behind a small interface Experimental and internal PyCharm package APIs are isolated to one replaceable implementation and can be faked in tests.
Treat stub installation as nonfatal A network or repository failure must not discard an otherwise valid generated project.
Prefer SDK installation over Sources Root attachment Site-packages is the normal interpreter-aware indexing path. A Sources Root is reserved for validated unpacked stubs when package installation is unavailable.
Reuse bpyApiInstallPath for fallback stubs The existing application setting provides one managed cache location; version-specific subdirectories prevent Blender API versions from colliding.

Generation sequence

  1. PyCharm validates the environment form.
  2. PyCharm creates or selects the SDK and assigns it to the existing Python module.
  3. The Blender settings object generates project directories, templates, source roots, and ProjectConfig defaults.
  4. The selected Blender major/minor resolves to a version-specific stub package.
  5. The package installer installs the stub into the assigned SDK's site-packages and records it as a development-only dependency where the package manager supports dependency groups.
  6. PyCharm refreshes package and SDK paths so import bpy becomes available to analysis without marking site-packages as a Sources Root.
  7. If package installation is unavailable and validated unpacked stubs exist under bpyApiInstallPath/<major.minor>, attach that version directory to the module as a Sources Root and refresh project roots.
Selected BlenderStub requirement
4.2.xfake-bpy-module-4.2
4.5.xfake-bpy-module-4.5
5.1.xfake-bpy-module-5.1 (upstream-confirmed, but not currently selected by BlenderVersions)
5.2.xNo confirmed package; require a verified future mapping or validated unpacked stubs
Constraint: Do not fall back to the rolling fake-bpy-module package for an unknown Blender release. Use only an explicitly verified version-specific package or a validated unpacked stub directory for the same Blender major/minor.

4) Implementation Plan

Tasks are ordered by dependency. Each checkbox has a testable completion condition.

Foundation

  • Replace the adapter inheritance in BlenderProjectDirectoryGenerator with PyV3ProjectBaseGenerator<BlenderProjectSettings> while retaining the directoryProjectGenerator registration.
  • Add a settings model implementing PyV3ProjectTypeSpecificSettings and move all Blender form state into it.
  • Add a UI implementation using PyV3ProjectTypeSpecificUI; keep common fields above the environment picker and detailed manifest and permission fields under Advanced Settings.
  • Preserve existing validation messages and move any remaining user-visible literals into MessageBundle.properties.

Scaffolding integration

  • Refactor BlenderProjectGenerator to accept the supplied Module, VirtualFile, and Sdk rather than discovering the first module.
  • Perform VFS, template, and source-root mutations through the required EDT/write actions and return PyResult failures instead of swallowing exceptions.
  • Keep the plugin responsible for src, Blender manifest, Python package metadata, examples, license, README, Git ignore rules, and ProjectConfig defaults.
  • Generate pyproject.toml before invoking package installation.

Linting stub installation

  • Add an “Install Blender API linting stubs” setting that defaults to enabled.
  • Add a pure resolver that maps a selected Blender version to fake-bpy-module-<major.minor> only when the version is supported.
  • Add BlenderPythonPackageInstaller and a production implementation backed by PythonPackageManager.forSdk(project, sdk).
  • Record the stub as a development-only dependency and install it into the SDK selected by PyCharm, verifying that it becomes visible through the SDK's site-packages roots.
  • Make repeated installation safe when the required package is already installed.
  • Add a fallback stub-root provider that resolves version-specific unpacked modules beneath PluginConfig.getCodeCompletionPath(), validates their expected top-level module layout, and attaches only the matching directory to the generated module as a Sources Root.
  • Ensure root attachment is idempotent, is performed through the module root model on the correct write thread, and never marks the SDK's own site-packages directory as a project Sources Root.
  • On installation failure with no valid fallback root, keep project generation successful, write diagnostic details through PluginLogger, and show a localized NotificationModal message containing the exact package requirement and Sources Root recovery instructions.

Legacy removal and documentation

  • Remove the generic wizard, wizard-data interface, directory-generator adapter, and custom legacy settings step after the PyV3 flow is verified.
  • Update project documentation and the generated README to replace manual interpreter and stub instructions with the automatic workflow and recovery steps.

5) Validation and Acceptance

  • Unit-test package resolution for Blender 4.2 and 4.5, the upstream-confirmed 5.1 package, current unsupported Blender 5.2, full patch versions, and an unknown release.
  • Test enabled, disabled, successful, already-installed, failed, and cancelled stub installation through a fake installer.
  • Test valid, missing, malformed, mismatched-version, already-attached, and external fallback Sources Root handling.
  • Test that package failure does not prevent Blender files or project configuration from being generated.
  • Test settings-to-manifest conversion and generation against the module supplied by PyCharm.
  • Run ./gradlew test --no-daemon.
  • Run ./gradlew compileKotlin --no-daemon.
  • Run plugin verification against PyCharm 2026.1.
  • Manually create projects with Project venv, Project uv, and an existing interpreter; confirm exactly one module, the selected SDK, generated Blender files, installation under the selected environment's site-packages, and code completion for import bpy.
  • Manually remove or disable the package, attach validated unpacked stubs through the fallback, and confirm import bpy completion from the Sources Root.
  • Commit Changes with [Feature -> wizard] Add native Python environments and Blender API stubs.

6) Risks and Mitigations

RiskMitigation
PyCharm packaging API changesKeep all experimental/internal calls in one installer implementation and cover its contract with fakes.
Network or repository unavailableComplete project creation and provide a retryable manual requirement.
Environment manager edits project structureDisable supportsNotEmptyModuleStructure and generate all Blender files in the type-specific phase.
Unsupported future Blender versionRequire an explicit package mapping before enabling automatic installation.
Linting stub leaks into runtime dependenciesStore it as a development-only dependency and keep it out of Blender packaging.
Stale or wrong fallback stubs are indexedUse version-specific subdirectories, validate the expected module layout, and attach only the directory matching the selected Blender major/minor.
Duplicate or overly broad project rootsCheck existing module roots before attachment and never mark the code-completion cache parent or SDK site-packages as a Sources Root.
