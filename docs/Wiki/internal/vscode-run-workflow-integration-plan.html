1) Scope

Integrate the run/debug lifecycle, not a one-off test script:

  • Launch Blender with a bootstrap Python entrypoint.
  • Bootstrap in Blender installs/loads helper modules.
  • Start a local Blender HTTP endpoint + debugpy and handshake back to IDE.
  • Support run script, reload addon, stop Blender messages.
  • Attach IDE debugger with path mappings.
Your current debug launch script template is a placeholder panel script. It is useful for proving launch-mode switching, but not for workflow parity.

2) What the VS Code Extension Actually Does

2.1 Process launch

  1. VS Code launches Blender with --python pythonFiles/launch.py.
  2. It injects env vars such as ADDONS_TO_LOAD, EDITOR_PORT, VSCODE_IDENTIFIER, log level, extension repository.
  3. It tracks process as a task and keeps instance metadata in-memory.

2.2 Blender-side bootstrap

  1. launch.py appends bundled include path and calls blender_vscode.startup(...).
  2. startup() ensures python deps (debugpy, requests, flask, werkzeug), sets up addon links, starts communication server, registers operators/UI, enables addon/extension.
  3. Blender sends setup payload back to editor (Blender port + debugpy port + mappings + identifier).

2.3 IDE-side orchestration

  1. Editor HTTP server receives setup payload.
  2. Editor attaches debugger to debugpy port with path mappings.
  3. Editor can send POST commands to Blender: reload, script, stop.

4) Target Architecture in This Plugin

4.1 Kotlin side (IDE)

  • Launcher keeps process launch logic and builds env variables + command line.
  • New Project service: BlenderRuntimeSessionService to track running instances (process handler, ports, instance id).
  • New local HTTP server (JDK HttpServer or Ktor embedded) to receive setup messages from Blender bootstrap.
  • New debugger bridge: attach PyCharm debugger to reported debugpy port with path mappings.

4.2 Python side (Blender runtime)

  • Replace placeholder launch templates with a real bootstrap package in plugin resources.
  • Bootstrap starts debugpy + Flask/Werkzeug server and registers action handlers.
  • Keep command contract close to VS Code payloads for easier parity and maintenance.
For maintainability: keep the Blender-side bootstrap as real Python resource files (like VS Code does), not as a large Kotlin-generated string/template.

5) Phased Implementation Plan

Phase 0: Stabilize current debug launch mode

  • Keep single run configuration type/factory.
  • Debug icon path uses debug mode and scratch bootstrap script creation via createFromTemplate.
  • Ensure internal template registration matches actual template names. (Current repo has BlenderBaseLaunchScript.py.ft and BlenderDebugLaunchScript.py.ft, not BlenderLaunchScript.py.ft.)

Phase 1: Introduce real bootstrap entrypoint

  • Add resource tree under plugin resources, equivalent to VS Code pythonFiles/include/blender_vscode/*.
  • Add one bootstrap script (e.g. BlenderRuntimeLaunch.py.ft) that imports package and calls startup.
  • In Launcher, generate/copy bootstrap to scratch and pass --python in debug mode.

Phase 2: Add IDE local server + handshake contract

  • Create BlenderEditorServerService that binds localhost random port.
  • Pass EDITOR_PORT and unique session identifier in env.
  • Handle setup payload from Blender: blenderPort, debugpyPort, path mappings, identifier.

Phase 3: Debugger attach integration

  • Create debug attach profile from setup payload and attach automatically.
  • Build path mappings from project source folder + addon symlink settings + scripts dir.
  • Add “just my code” equivalent setting and map it to debugger attach options.

Phase 4: Runtime commands (script/reload/stop)

  • IDE action endpoints to send JSON commands to active Blender instance(s).
  • Blender operators/actions for reload, run script with context, stop.
  • Expose actions in tool window and optionally editor gutter/context commands.

Phase 5: Compatibility hardening

  • Keep Blender <4.2 legacy addon path behavior and 4.2+ extension repo behavior.
  • Handle missing pip/deps with clear notifications.
  • Add cancellation/timeouts and stale session cleanup.

6) Settings/State Changes

Add project-scoped fields to ProjectConfig (or plugin-scoped to PluginConfig where global):

  • reloadOnSave: Boolean
  • justMyCode: Boolean
  • extensionsRepository: String
  • environmentVariables: Map<String, String>
  • scriptDirectories: List<String> (optional)

Tool window/settings UI should edit these consistently and write through same state service.

Windows symlink/junction permissionsAddon load failuresMirror VS Code’s junction approach and robust error messaging.
Template driftRuntime mismatchPrefer packaged Python resources over heavy templates for core logic.

8) Acceptance Checklist

  • Run icon starts Blender with project args and no debugger attach.
  • Debug icon starts Blender, bootstrap initializes, and debugger auto-attaches.
  • Addon source changes can be reloaded from IDE command without restarting Blender.
  • Script execution command works against already-running Blender session.
  • Stop command shuts down specific session and cleans local state.
  • Blender 4.1 (legacy addon path) and 4.2+ (extensions repo) both work.
  • Failure paths surface precise errors in Notification + plugin logs.
