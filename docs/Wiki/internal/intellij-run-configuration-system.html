IntelliJ Run Configuration System

Source-level architecture reference using local intellij-community checkout

Scope: how configuration types are registered, created from context, persisted, launched through executors/runners, and rendered in Run/Debug UI.

1) Mental Model

The Run Configuration system is a layered pipeline:

  1. Definition layer: ConfigurationType + ConfigurationFactory + RunConfiguration.
  2. Selection layer: user chooses an Executor (Run/Debug/etc.) and the platform finds a compatible ProgramRunner.
  3. Preparation layer: RunProfile.getState() creates a RunProfileState (often CommandLineState).
  4. Execution layer: ExecutionManager runs before-launch tasks, starts process, and wires toolwindow content.
  5. Persistence/UI layer: RunManager owns saved settings, templates, temporary configs, and selected config.

2) Core APIs and Responsibilities

APIRole
RunManagerProject service for config list, templates, selected config, temporary/permanent lifecycle.
RunnerAndConfigurationSettingsPersisted wrapper around a RunConfiguration plus per-runner data and storage mode.
ConfigurationTypeType descriptor shown in UI (id/display/icon/factories).
ConfigurationFactoryCreates template configuration instances; controls IDs/defaults/singleton policy.
RunConfigurationBaseBase implementation with options state, before-run task list, serialization hooks.
LocatableConfigurationBaseAdds generated-name behavior for context-produced configurations.
ExecutorExecution mode (Run/Debug/etc.) and its UI identity/icons/action text.
ProgramRunnerLaunch strategy for a given executor + run profile combination.
ExecutionEnvironmentImmutable launch context containing profile, executor, target, runner, settings, reuse content.
RunProfileStateExecutable runtime state; creates process/console result.
CommandLineStateStandard state helper that builds console + process handler result.
ExecutionManagerCoordinates start flow, before-run tasks, content tabs, restart, active launches.

3) Extension Points and Plugin Registration

Primary EP names:

  • com.intellij.configurationType
  • com.intellij.executor
  • com.intellij.programRunner
  • com.intellij.runConfigurationProducer
  • com.intellij.stepsBeforeRunProvider
  • com.intellij.runLineMarkerContributor
  • com.intellij.runConfigurationExtension (Java execution module)

Platform wiring examples:

<executor implementation="com.intellij.execution.executors.DefaultRunExecutor" id="run"/>
<configurationType implementation="com.intellij.execution.compound.CompoundRunConfigurationType"/>
<programRunner implementation="com.intellij.execution.runners.DefaultRunProgramRunner"/>

Project services are also registered here, especially:

<projectService serviceInterface="com.intellij.execution.RunManager"
                serviceImplementation="com.intellij.execution.impl.RunManagerImpl"/>
<projectService serviceInterface="com.intellij.execution.ExecutionManager"
                serviceImplementation="com.intellij.execution.impl.ExecutionManagerImpl"/>

4) Creation Flows (Manual + Context + Gutter)

Manual creation

In “Edit Configurations”, IDE uses ConfigurationType and ConfigurationFactory to create a template-derived instance, then persists via RunManager.

Context creation

RunConfigurationProducer (or LazyRunConfigurationProducer) maps PSI location to a configuration. If no matching existing config is found, a new one is created from template and usually auto-named.

Gutter run icon integration

RunLineMarkerContributor adds executable gutter actions and can optimize context action behavior by declaring whether it produces all possible configurations for a file.

5) Execution Pipeline (Run/Debug)

  1. User triggers Run/Debug on selected configuration.
  2. ExecutionEnvironmentBuilder builds ExecutionEnvironment with executor, target, runner, profile, settings.
  3. Runner is resolved by ProgramRunner.getRunner(executorId, runProfile).
  4. runProfile.getState(executor, environment) returns runtime state.
  5. ExecutionManager.startRunProfile(...) starts lifecycle and content reuse logic.
  6. Runner executes state; for command-line states this usually means state.execute() and resulting process handler + console are shown.
  7. RunContentManager displays the descriptor in Run/Debug toolwindow.
Important split: RunConfiguration decides what to run and builds state; ProgramRunner decides how that state is launched for a given executor.

6) Before-Run Tasks and Execution Targets

Before launch tasks

BeforeRunTaskProvider extensions define configurable tasks (build scripts, compile steps, tooling tasks) attached per configuration/template.

Execution targets

ExecutionTargetManager controls active target and target compatibility checks. ExecutionEnvironment can also resolve and prepare target environments for remote/target-aware execution.

7) Persistence and Storage Model

RunnerAndConfigurationSettings supports three storage modes:

  • Local workspace: non-shared (.idea/workspace.xml)
  • Shared dot-idea: .idea/runConfigurations/*.xml
  • Arbitrary project file: *.run.xml under project content

RunManagerImpl also tracks templates, temporary configs, selected config, and unique naming policy.

8) Customization Hooks

  • RunConfigurationExtension: patch/augment already-created run configurations (notably Java execution path).
  • Language- or framework-specific extension managers (for example Python has dedicated run configuration extension EP namespace).
  • Custom SettingsEditor for run config UI.
  • BeforeRunTaskProvider for pre-launch orchestration.
  • ExecutionEnvironmentProvider for custom environment construction.

9) Concrete Examples (Java, Python, This Plugin)

Java (platform module)

intellij.java.execution.impl.xml registers Java application configuration types, producers, and default Java run runner.

Python (platform module)

Python registers PythonConfigurationType, PythonRunner (Run executor), PythonDebugProgramRunner (Debug executor), producers, and Python run line marker contributors.

This repository plugin

com.sakurasedaia.blenderdevelopment.run.BlenderConfigurationType registers a single factory and template config. BlenderLaunchRunConfiguration validates project config and returns a CommandLineState that starts Blender via plugin launcher service, with runtime bootstrap enabled by default for Run and Debug.
