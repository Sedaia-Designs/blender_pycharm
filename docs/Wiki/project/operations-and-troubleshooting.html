1) Installation Scan Behavior

BlenderInstallationScanner probes OS-specific locations and caches results in PluginConfig.detectedBlender.

  • Windows: common Program Files roots for Blender Foundation install pattern
  • macOS: /Applications and ~/Applications bundle scan
  • Linux: which blender-runtime, common binary paths, Linux Homebrew roots

2) Notifications and Logs

Feedback path:

  1. PluginLogger writes structured log details.
  2. NotificationModal sends info/warn/error user notifications.
  3. MessageBundle.properties centralizes message text and formatting keys.

3) Common Failures

Add-on not loaded ... module loaded with no associated fileReload attempted legacy add-on module name for an extension-like directory (namespace package/no valid __init__.py)Runtime refreshes addon/extension indices before enable, then resolves extension fallback from blender_manifest.toml:id and discovered Blender extension modules (instead of only folder-name guessing).

4) Triage Checklist

  1. Check ProjectConfig for Blender path and source folder values.
  2. Check plugin log output path configured in PluginConfig.
  3. Validate runtime extraction directory has current version marker.
  4. Re-run install scan and inspect scan warnings (probe failures vs inaccessible roots).
  5. Re-run with minimal run arguments to isolate CLI issues.

5) Complex API Snippets

Async install scan orchestration

ApplicationManager.getApplication().executeOnPooledThread {
  project.getService(BlenderInstallationScanner::class.java).refreshInstalledVersionsCache()
  val installs = PluginConfig.getInstance().getDetectedBlenderInstalls()
  notifications.sendInfo(MessageBundle.message("notification.settings.scan.completed.found", installs.size.toString()))
}

External process capture result handling

val result = ExternalProcessBuilder(project).launchAndCaptureOutput("which", "blender-runtime")
if (result.cancelled || result.failure != null || result.exitCode != 0) return null
val locatedPath = result.firstLine.trim()
